## Corrected Understanding (superseding part of 01-requirements.md)

Requirements assumed the stub `UnimplementedError` from `MacosFlutterGsm`/
`WindowsFlutterGsm` would propagate uncaught to the example's UI, since
`main.dart` only catches `ModemException`. **Reading
`ModemRepositoryImpl` (`lib/src/data/repositories/modem_repository_impl.dart`)
shows this is already handled by the library**:

```dart
Future<T> _guard<T>(Future<T> Function() call) async {
  try {
    return await call();
  } on UnimplementedError catch (_) {
    throw const ModemDriverNotAvailableException();
  }
}
```

`ModemDriverNotAvailableException extends ModemException`
(`modem_exceptions.dart`). The example instantiates
`ModemRepository _repository = ModemRepositoryImpl();` — so every call
through `_repository` already gets `UnimplementedError` converted to a
typed `ModemException` subclass *before* it reaches `main.dart`'s
`on ModemException catch (e)` blocks in `_refresh()`/`_dial()`/`_sendSms()`.

**Empirically verified** in a throwaway scratch copy (not committed, not
part of the real working tree): scaffolded `macos/` via `flutter create`,
ran `flutter build macos --debug` (succeeded), launched the built
`.app`, and confirmed the process stays alive (no crash) — `listModems()`
hitting `MacosFlutterGsm`'s stub surfaces as
`ModemDriverNotAvailableException` ("Modem driver is not available on
this platform yet"), rendered in the existing red-text error `ListView`,
exactly like any other `ModemException`.

**Conclusion**: Acceptance Criterion 2 from requirements ("catch it
distinctly ... show a clear message instead of crashing") is **already
satisfied by existing code, on both this repository's `main.dart` and
`flutter_gsm` library** — no new error-handling code is needed. This
flow only needs to *verify* that behavior once real platform folders
exist, not add a new catch clause. (The displayed text is prefixed with
`ModemException:` per `ModemException.toString()` — readable enough;
polishing that prefix is optional, not required to meet the criterion.)

## Dependency Cleanup — exact set

Verified via `grep -rl "package:X" lib/` across **all** of `example/lib/`
(not just `main.dart`) before deciding removal, so nothing silently
used only by theme/utils/l10n gets cut without accounting for it:

**Remove from `pubspec.yaml` `dependencies:`** (zero usages anywhere in
`example/lib/` once `theme/`, `utils/`, `l10n/` are deleted):
`provider`, `shared_preferences`, `flutter_svg`, `google_fonts`,
`device_info_plus`, `permission_handler`, `crypto`, `logger`, `http`,
`connectivity_plus`, `workmanager`, `intl`, `dartz`, `equatable`,
`get_it`, `flutter_local_notifications`, `collection`,
`flutter_localizations` (sdk), `cupertino_icons`.

- `intl` and `flutter_localizations` are *not* in the original 15
  flagged in requirements — confirmed via grep that their only 25 usage
  sites are all inside `lib/l10n/app_localizations*.dart`, so they
  become removable once that directory is deleted. Adding them to the
  removal list; requirements' Acceptance Criterion 3 ("every dependency
  actually used") governs, so this is in-scope, not scope creep.
- `cupertino_icons` has zero usages anywhere in `example/lib/` (grep
  confirmed) despite being a standard `flutter create` default — remove
  it too per the same "every dependency actually used" criterion. Flagged
  explicitly here since removing it is slightly unusual for a Flutter
  template default; if Anton prefers keeping it as inert convention,
  that's a one-line revert in the plan/implementation review.
- Also remove the `generate: true` line from `pubspec.yaml`'s `flutter:`
  section (only meaningful with `lib/l10n/` + arb files present; no
  `l10n.yaml` exists, and nothing references `AppLocalizations`).

**Keep**: `flutter` (sdk), `flutter_gsm` (path dep — the library under
test), `flutter_test` (dev, sdk), `flutter_lints` (dev) — all actually
used (`main.dart` imports `flutter/material.dart` and
`flutter_gsm/flutter_gsm.dart`; `flutter_test`/`flutter_lints` back the
test/analyzer tooling used to verify this very flow).

**Keep unconditionally, do not touch**: `dependency_overrides` block
(`plugin_platform_interface: ^2.1.8`, `flutter_dialer: {path:
../../flutter_dialer}`) — required for the monorepo's version-constraint
workaround per that block's own comment; unrelated to this cleanup.

## Edge Cases

- **macOS Swift Package Manager warnings**: `flutter build macos` warns
  that `connectivity_plus`, `device_info_plus`, `flutter_local_notifications`
  don't support SPM (plus `flutter_smsussd`, pulled in transitively by
  `flutter_gsm` itself for Android — not removable, it's the library's
  dependency, not the example's). Non-blocking (confirmed: build still
  succeeds) and moot for three of the four once the example's own
  cleanup drops them from its direct dependency list; `flutter_smsussd`'s
  warning persists regardless (out of scope — it's `flutter_gsm`'s
  dependency, not example's, and the library isn't to be touched).
- **Android regression risk**: cleanup only touches `example/pubspec.yaml`
  and `example/lib/{theme,utils,l10n}` — `example/android/` isn't
  edited, so Android build should be unaffected. Should-Have from
  requirements: run `flutter build apk --debug` (or at minimum
  `flutter analyze` with an Android-targeted config, though `flutter
  analyze` isn't platform-scoped) after cleanup to confirm no regression.
- **`flutter_dialer`/`flutter_tele`/`flutter_smsussd` path deps**: these
  are the *library's* dependencies (declared in `flutter_gsm/pubspec.yaml`,
  not `example/pubspec.yaml`) and flow through transitively — nothing
  for this flow to change here, just confirmed not to break under the
  new platform folders (macOS build already succeeded with them present
  transitively).
