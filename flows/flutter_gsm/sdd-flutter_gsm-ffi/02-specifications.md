# Specifications: sdd-flutter_gsm-ffi

> Version: 1.0
> Status: DRAFT
> Last Updated: 2026-08-21

## Architecture Overview

```
ModemRepository (interface, unchanged)
        |
ModemRepositoryImpl (unchanged — already wraps UnimplementedError)
        |
LinuxFlutterGsm (rewritten: dial/answer/hangup/sms/ussd/at/imei/diag/
                 power/restart real; setGroup local-only; setNetworkMode
                 real but unverified mode codes)
        |
SimboxFfiBindings (new — generated by `ffigen` from simbox_api.h/
                    simbox_types.h, thin Dart<->C signature layer only,
                    no logic)
        |
SimboxNativeLibrary loader (new — DynamicLibrary.open with the fallback
                             path strategy below)
        |
libsimbox.so / .dylib   (native, from libsCpp/asterisk_chan_simbox;
                          discovery<->registry fix lands here too)
```

Three new Dart files in `flutter_gsm`:
- `lib/src/ffi/simbox_bindings.dart` — `ffigen`-generated raw FFI
  signatures (regenerated from source headers, not hand-maintained).
- `lib/src/ffi/simbox_native_library.dart` — library loading
  (`DynamicLibrary.open`) with the path-resolution strategy below.
- `lib/src/linux/simbox_modem_repository.dart` — the real logic: owns a
  `simbox_handle_t`, converts between `ModemDevice`/`ModemCall`/
  `AtCommandResult` and C structs, manages the event-callback bridge,
  and is what `LinuxFlutterGsm` delegates every method to.

One change on the native side, inside
`libsCpp/asterisk_chan_simbox/src/` (adapter-layer, in-bounds per
requirements):
- `simbox_discovery.c`'s `simbox_discovery_scan()` currently always sets
  `ctx->count = 0` (comment says "Scan /sys/bus/usb/devices on Linux or
  simulate on other platforms" but doesn't actually do either). Real
  `/sys/bus/usb/devices` enumeration is out of scope for *this* flow's
  native fix (it's a substantial USB-enumeration task on its own,
  overlapping with `sdd-asterisk-chan-simbox`'s own remit) — this flow's
  native fix is narrower: **wire whatever `simbox_discovery_scan()`
  finds into the device registry** via a new, header-exposed
  `simbox_device_register(simbox_handle_t handle, const
  simbox_discovered_device_t *discovered)` function that constructs a
  `simbox_device_t` (using the existing internal `simbox_device_create`)
  from a `simbox_discovered_device_t` and appends it to
  `inst->devices[]`. This closes the *registry* gap; whether
  `simbox_discovery_scan()` itself finds real devices is bounded by
  whatever `sdd-asterisk-chan-simbox` already implemented there — verify
  during implementation, flag back if it's still a stub.

## FFI Binding Generation

Use `package:ffigen` (dev dependency), configured via
`ffigen.yaml` pointing at `simbox_api.h` (which transitively includes
`simbox_types.h`) from `libsCpp/asterisk_chan_simbox/src/`. Regenerate
`lib/src/ffi/simbox_bindings.dart` via `dart run ffigen` whenever the C
header changes — never hand-edit the generated file. Rationale: hand-
maintaining ~30 function signatures plus 5 structs (`simbox_device_info_t`,
`simbox_discovered_device_t`, `simbox_event_t` with its nested union,
`simbox_config_t`, callback typedefs) by hand is exactly the kind of
error-prone bookkeeping `ffigen` exists to eliminate — the project has no
existing FFI precedent to match either way.

`simbox_event_t`'s tagged union (`data` field, a C `union` keyed by
`type`) is the one place `ffigen` output needs a thin hand-written
wrapper on top (reading the right union arm based on `event->type`,
since Dart FFI structs expose unions as raw byte layout, not
discriminated access).

## Native Library Loading

**Must Have (this flow)**: pragmatic path resolution, not full app
bundling — getting real I/O working is the priority; packaging is a
known, called-out follow-up.

```dart
DynamicLibrary _loadSimbox() {
  final envPath = Platform.environment['FLUTTER_GSM_SIMBOX_LIB'];
  if (envPath != null) return DynamicLibrary.open(envPath);

  // Monorepo-relative fallback: works for the example app and any
  // consumer running from within this workspace without a packaging
  // step. Computed from Platform.script / a fixed relative offset from
  // this package's own location is NOT reliable across build outputs —
  // instead resolve relative to the current working directory, which is
  // how `flutter run`/`flutter test` invoke things from a known repo
  // path. Document this constraint loudly; it is a dev-mode convenience,
  // not a production strategy.
  final candidates = [
    'libsimbox.so',                                    // system-installed
    'libsimbox.dylib',
    '../../libsCpp/asterisk_chan_simbox/libsimbox.so',  // monorepo dev path
    '../../libsCpp/asterisk_chan_simbox/libsimbox.dylib',
  ];
  for (final path in candidates) {
    try {
      return DynamicLibrary.open(path);
    } catch (_) {
      continue;
    }
  }
  throw const ModemDriverNotAvailableException();
}
```

**Should Have (flagged as explicit follow-up, not silently deferred)**:
a real `linux/CMakeLists.txt` in `flutter_gsm` that builds `libsimbox`
from `libsCpp/asterisk_chan_simbox`'s own Makefile as part of the
Flutter Linux build and installs the resulting `.so` alongside the app's
bundled libraries (the standard way Flutter Linux plugins ship native
code) — needed before this is redistributable outside the monorepo.
Tracked as an open item in `_status.md`, not blocking this flow's Must
Have.

`SimboxNativeLibrary` catches `ArgumentError`/any `DynamicLibrary.open`
failure and surfaces `ModemDriverNotAvailableException` — matching
`ModemRepositoryImpl`'s existing `UnimplementedError` → typed-exception
convention (Acceptance Criterion 5), so callers see one consistent
failure mode whether the platform is unimplemented or the library
genuinely isn't found.

## Identity Mapping

`modemId: String` = `simbox_device_sn` (serial number), **not** the raw
`simbox_device_t` pointer. `SimboxModemRepository` keeps an internal
`Map<String, Pointer<Void>>` (serial number -> device handle) populated
on each `listModems()`/discovery event, and every method taking a
`modemId` looks up the handle through this map, throwing
`ModemNotFoundException(modemId)` (already exists, used identically by
`FakeModemRepository` in `simbox-app`) if the serial isn't currently
tracked. This mirrors `flutter_gsmsip`'s `SipRepositoryImpl` pattern of
never exposing raw native handles across the repository boundary
(`_requireTrackedAccount`/`_requireTrackedCall`), applied here as
`_requireTrackedDevice`.

`ModemCall`/call-id handling: `simbox_api.h` has no separate call handle
— calls are operations *on* a `simbox_device_t` (`simbox_call_originate`
etc. take the device, not a call object), and a device can only have one
call at a time (`simbox_device_state_t` is a single enum per device, not
a call list). So `callId` in `ModemRepository.hangupCall(callId)`/
`answerCall(callId)` is synthesized as the same string as `modemId`
(`dial()` returns a `ModemCall` whose `id` is the modem's serial number)
— there is exactly one in-flight call per modem, consistent with the
underlying hardware (one modem = one voice channel). Document this
explicitly since it differs from SIP's separate call-id concept.

## Event Bridging

`simbox_set_event_callback` takes a C function pointer
(`simbox_event_cb`) that `libsimbox` may invoke from any thread it
spawns internally (the codebase uses `pthread` throughout). Bridging
this into a Dart `Stream<ModemEvent>` safely requires
`NativeCallable.listener` (Dart 3's isolate-safe FFI callback
mechanism — the only one safe to invoke from a non-Dart-owned thread;
a plain `Pointer.fromFunction` callback is **not** safe here and would
corrupt the Dart VM if called off the main isolate).

```dart
late final NativeCallable<SimboxEventCbNative> _eventCallable;
final _eventController = StreamController<ModemEvent>.broadcast();

void _init() {
  _eventCallable = NativeCallable<SimboxEventCbNative>.listener(_onNativeEvent);
  bindings.simbox_set_event_callback(_handle, _eventCallable.nativeFunction, nullptr);
}

void _onNativeEvent(Pointer<simbox_event_t> event) {
  // dereference event.ref, switch on event.ref.type, read the matching
  // union arm, look up modemId via device_sn -> map to the right
  // ModemEvent subtype, add to _eventController.
}
```

Mapping table (`simbox_event_type_t` -> `ModemEvent` subtype):

| Native event | `ModemEvent` subtype |
|---|---|
| `SIMBOX_EVENT_DEVICE_CONNECTED` | `ModemAttached` (device re-fetched via `simbox_device_get_by_sn` for full info) |
| `SIMBOX_EVENT_DEVICE_DISCONNECTED` | `ModemDetached` |
| `SIMBOX_EVENT_INCOMING_CALL` | `ModemCallStateChanged` (state `incoming`) |
| `SIMBOX_EVENT_CALL_STATE_CHANGED` | `ModemCallStateChanged` |
| `SIMBOX_EVENT_INCOMING_SMS` | `ModemSmsReceived` |
| `SIMBOX_EVENT_USSD_RESPONSE` | `ModemUssdReceived` |
| `SIMBOX_EVENT_BALANCE_UPDATE` | *(no `ModemEvent` subtype exists — dropped for now, logged; balance isn't a tracked `ModemDevice` field either. Flag as a follow-up if balance tracking is wanted, don't invent a field silently.)* |
| `SIMBOX_EVENT_DEVICE_ERROR` | `ModemErrorOccurred` |
| `SIMBOX_EVENT_PROG_PROGRESS` | *(DIAG-programmator progress — out of scope, `ModemRepository` has no programmator concept; dropped)* |

`simbox_device_state_t` -> `CallState`/`ModemState` mapping (both
enums already exist in `flutter_gsm`):

| `simbox_device_state_t` | `ModemState` | `CallState` (when relevant) |
|---|---|---|
| `SIMBOX_STATE_DISCONNECTED` | `removed` | — |
| `SIMBOX_STATE_CONNECTING` | `init` | — |
| `SIMBOX_STATE_IDLE` | `registered` | — |
| `SIMBOX_STATE_RINGING` | `callActive`* | `incoming` |
| `SIMBOX_STATE_DIALING` | `callActive`* | `initiated` |
| `SIMBOX_STATE_ACTIVE_CALL` | `callActive` | `active` |
| `SIMBOX_STATE_HOLD` | `callOnHold` | `held` |
| `SIMBOX_STATE_ERROR` | `error` | — |
| `SIMBOX_STATE_DIAGNOSTIC` | `error`* | — |

*Starred rows: `ModemState` has no dedicated "ringing"/"dialing"/
"diagnostic" value (checked `modem_state.dart`'s real enum — only
`init`/`registering`/`registered`/`ready`/`callActive`/`callOnHold`/
`error`/`removed` exist) — mapped to the closest existing value rather
than adding new enum cases not requested by this flow. If finer-grained
UI states are wanted later (e.g. `simbox-app`'s call screen wants to
show "ringing" distinctly), that's a `ModemState` enum addition to
propose separately, not smuggled in here.

## Method-by-Method Mapping

| `ModemRepository` method | Native call | Notes |
|---|---|---|
| `listModems()` | `simbox_device_count` + `simbox_device_get_by_index` loop, `simbox_device_get_info` per device | Populates the serial->handle map |
| `getModem(modemId)` | `simbox_device_get_by_sn` + `simbox_device_get_info` | Throws `ModemNotFoundException` if absent |
| `modemEvents` | event-callback bridge (above) | |
| `sendAtCommand(modemId, cmd, {timeout})` | `simbox_at_command` | `timeout` param has no native equivalent — `simbox_at_command` is synchronous/blocking in the C API; enforce the Dart-side timeout via `.timeout()` on the async wrapper (the FFI call itself runs on a background isolate/thread via `Isolate.run` or similar — direct synchronous FFI calls block the calling isolate, see Threading below) |
| `setDiagMode(modemId, enabled)` | `simbox_prog_open(tty_port)` + `simbox_prog_set_diagmode` (enabled=true only; no "disable diag mode" function exists in `simbox_api.h` — `enabled=false` throws `UnsupportedError`, a real gap, not invented) | Needs the device's `tty_data` port path from `simbox_device_info_t`, not just its handle — `simbox_prog_t` is a separate handle type from `simbox_device_t` |
| `setPower(modemId, {on})` | `on=true`: `simbox_at_command(dev, "AT+CFUN=1,1\r", ...)`; `on=false`: `simbox_at_command(dev, "AT+CFUN=0\r", ...)` | `AT+CFUN=1,1` confirmed from chan_svistok source (`at_command.c`'s `at_enque_reset`, README.txt); `AT+CFUN=0` is standard 3GPP but **not** confirmed against real hardware in this codebase — flag as implementation-time verification |
| `restartModem(modemId, {mode})` | `simbox_at_command(dev, "AT+CFUN=1,1\r", ...)` | `mode` (`now`/`graceful`/`whenConvenient`) has no AT-level equivalent — `graceful`/`whenConvenient` implemented in Dart by checking `simbox_device_state(dev) == SIMBOX_STATE_ACTIVE_CALL` and deferring (poll or wait for the next `ModemCallStateChanged` event showing the call ended) before issuing the AT command |
| `changeImei(modemId, imei)` | `simbox_change_imei` | Direct mapping |
| `setNetworkMode(modemId, mode)` | `simbox_at_command(dev, "AT^SYSCFG=<code>,0,3FFFFFFF,0,3\r", ...)` | Only `gsmOnly` (`code=13`) confirmed from chan_svistok's `README.txt`; `auto`/`wcdmaOnly` codes are **not** in the reference source anywhere — must be found in the actual attached modem's AT command reference during implementation. If they can't be confirmed, `setNetworkMode` for those two values throws `UnsupportedError` rather than guessing a wrong mode code (wrong `AT^SYSCFG` values can lock a modem to a network it can't reach) |
| `setGroup(modemId, groupId)` | **none** | Pure Dart-side local state — `groupId` is an app-level organizational concept (matches `flutter_gsmsip`'s old `ModemGroupConfig`), not a modem property `libsimbox`/chan_svistok has ever modeled. `SimboxModemRepository` keeps a local `Map<String, String>` (serial -> groupId), persisted the same way other `flutter_gsm` local state is (see Open Question below — no existing local-persistence pattern in this package yet) |
| `dial(modemId, number)` | `simbox_call_originate` | Returns synthesized `ModemCall` (id = modemId, per Identity Mapping above) |
| `hangupCall(callId)` | `simbox_call_hangup` (looked up via callId==modemId) | |
| `answerCall(callId)` | `simbox_call_answer` | |
| `sendSms(modemId, number, text)` | `simbox_sms_send` | |
| `sendUssd(modemId, code)` | `simbox_ussd_send` | Native signature returns `int` (status), not the USSD response text directly — the actual response text arrives asynchronously via `SIMBOX_EVENT_USSD_RESPONSE`. `ModemRepository.sendUssd` returns `Future<String>` (the response) per its existing signature — implemented by sending the command then awaiting the next matching `ModemUssdReceived` event for that `modemId`, with a timeout (10s, matching `sendAtCommand`'s default) |

## Threading

Blocking FFI calls (`simbox_call_originate`, `simbox_at_command`, etc.)
must not run on Dart's main isolate — they'd freeze UI frame rendering
for however long the native call blocks (AT command round-trips can
take seconds). Every `SimboxModemRepository` method wraps its native
call in `Isolate.run(...)` (simple, no persistent isolate/port
management needed for this flow's call volume) **except** ones that
must run on the isolate owning the `NativeCallable.listener` — verify
during implementation whether `Isolate.run`'s ephemeral isolate can
safely call into the same native library instance (it can, since
`dart:ffi` `Pointer`/`DynamicLibrary` handles are process-global, not
isolate-scoped — only Dart-side native callback registration is
isolate-sensitive).

## Edge Cases

- **`libsimbox` not found at all** (dev machine without the library
  built): `SimboxNativeLibrary` throws `ModemDriverNotAvailableException`
  at first use, not at plugin-registration time — matches existing
  `ModemRepositoryImpl` behavior for `UnimplementedError`, and avoids
  crashing app startup on platforms/dev machines where the library is
  legitimately absent.
- **Native call returns non-zero without an event**: most `simbox_*`
  functions return `int` (0 = success). Non-zero without a corresponding
  `SIMBOX_EVENT_DEVICE_ERROR` is mapped to a generic `ModemException`
  with the raw C return code in the message (no richer error taxonomy
  exists on the C side to draw from).
- **Device disappears mid-call** (unplugged): relies on
  `SIMBOX_EVENT_DEVICE_DISCONNECTED` firing; `SimboxModemRepository`
  removes the serial from its tracked-device map on that event, so a
  subsequent `hangupCall` on the now-stale `callId` correctly throws
  `ModemNotFoundException` rather than dereferencing a freed handle —
  **critical**: must remove from the map *before* any possible reuse,
  and must not call `simbox_device_destroy` from Dart at all (per
  `simbox_shutdown`'s own cleanup loop, only the native side owns
  device lifetime).
- **`setDiagMode(modemId, false)`**: no native "exit diag mode" —
  throws `UnsupportedError`, matching the AT-command/firmware methods'
  existing "no Android equivalent" pattern used elsewhere in this
  package (consistent unsupported-operation convention).
- **Two Dart isolates both calling `simbox_init`**: out of scope —
  `SimboxModemRepository`/`LinuxFlutterGsm` are constructed once via
  `FlutterGsmPlatform.instance`, matching every other platform
  implementation in this package; multi-isolate use was never a
  requirement.

## Testing Strategy

- **Unit tests for mapping/marshalling logic** (state enum conversion,
  event-type dispatch, AT-command string construction) — pure Dart, no
  native library needed, run in `flutter test` like every other test in
  this package.
- **Integration test against the real `libsimbox`** — new
  `test/simbox_modem_repository_integration_test.dart`, gated behind an
  environment check (skip if `libsimbox` can't be loaded, e.g. in CI
  without the library built) so it doesn't break the existing green
  `flutter test` baseline on machines without it. Exercises the same
  lifecycle as `tests/test_simbox.c` (init -> discover -> device ops ->
  shutdown) but from the Dart side, plus the new discovery->registry
  wiring this flow adds natively.
- **Native-side**: extend `tests/test_simbox.c` with a test for
  `simbox_device_register()` (the new function) proving a
  `simbox_discovered_device_t` becomes a queryable `simbox_device_t`
  without the `simbox_device_create()` test-only shortcut — satisfies
  Acceptance Criterion 4 directly.

## Non-Goals (reaffirmed from requirements)

- Windows/macOS FFI wiring, DIAG programmator/APDU reader exposure
  through `ModemRepository`, Android (unaffected), real
  `/sys/bus/usb/devices` enumeration inside `simbox_discovery_scan()`
  (bounded to whatever `sdd-asterisk-chan-simbox` already has there).

## Open Questions Resolved / Remaining

- ✅ Library loading: pragmatic env-var + monorepo-relative fallback for
  this flow; full CMake bundling flagged as an explicit follow-up.
- ✅ `modemId` mapping: serial number, confirmed.
- ✅ `setPower`/`restartModem` AT strings: `AT+CFUN=1,1` confirmed from
  source; `AT+CFUN=0` (power off) unconfirmed against real hardware.
- ⚠️ `setNetworkMode`'s `auto`/`wcdmaOnly` `AT^SYSCFG` codes: only
  `gsmOnly` (13) is confirmed from source — the other two remain open,
  to resolve during implementation against real hardware or vendor AT
  references, not guessed here.
- ⚠️ New: where does `groupId` local state persist? No existing local-
  persistence pattern in `flutter_gsm` (unlike `flutter_gsmsip`, which
  had `shared_preferences`). Proposing in-memory only for this
  iteration (lost on process restart) unless Anton wants
  `shared_preferences` added as a new dependency — flagging rather than
  silently adding a dependency.
