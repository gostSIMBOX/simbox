# ADR 003: Promise Callback Pattern

> **Status**: DRAFT  
> **Type**: Constraining  
> **Generated by**: /legacy analysis

---

## Context

The react-native-tele module bridges JavaScript code to native Android modules via React Native's NativeModules API. Native module methods are asynchronous and require callback-based communication.

React Native native modules typically use this callback pattern:
```java
// Android native module
@ReactMethod
public void makeCall(String destination, Callback successCallback, Callback errorCallback) {
    // ... implementation
    if (success) {
        successCallback.invoke(true, callData);
    } else {
        errorCallback.invoke(errorData);
    }
}
```

## Problem

How should the JavaScript layer handle native module callbacks and expose them to applications?

**Requirements**:
1. Native callbacks must be handled
2. Applications need Promise-based API (modern JavaScript standard)
3. Error handling must be consistent
4. Success/error data must be properly formatted

## Decision

**Chosen**: Wrap all native callbacks in Promises using a consistent `(successful, data)` tuple pattern.

All call control methods follow this implementation pattern:

```javascript
answerCall(call) {
    return new Promise((resolve, reject) => {
        NativeModules.TeleModule.answerCall(call.getId(), (successful, data) => {
            if (successful) {
                resolve(data);
            } else {
                reject(data);
            }
        });
    });
}
```

### Pattern Characteristics

1. **Single Callback**: Native module receives one callback with two parameters
2. **Success Flag**: First parameter `successful` is boolean indicating success/failure
3. **Data Parameter**: Second parameter `data` contains either result or error
4. **Promise Wrapping**: Callback wrapped in Promise for modern async/await support

### Usage Example

```javascript
// Success case
try {
    const result = await endpoint.answerCall(call);
    console.log('Call answered:', result);
} catch (error) {
    console.error('Failed to answer:', error);
}

// Or with .then()/.catch()
endpoint.answerCall(call)
    .then(data => console.log('Success:', data))
    .catch(error => console.error('Error:', error));
```

## Consequences

### Positive

1. **Modern API**: Applications can use async/await syntax
2. **Error Handling**: Standard try/catch for errors
3. **Consistency**: All methods follow same pattern
4. **Composability**: Promises can be chained and combined
5. **Type Safety**: Can define return types for Promise resolution

### Negative

1. **Non-Standard Callback**: `(successful, data)` tuple is custom pattern
2. **Error Object Loss**: Error data may not be proper Error objects
3. **Stack Traces**: Native errors may lose stack trace information
4. **Debugging**: Harder to debug errors without proper Error objects

### Neutral

1. **Extra Wrapper**: Promise wrapping adds minimal overhead
2. **Data Format**: Applications must understand data structure returned

## Implementation Details

### Method Signatures

All call control methods return `Promise<any>`:

| Method | Returns | Rejects With |
|--------|---------|--------------|
| `start(config)` | `{ accounts, calls, ...extra }` | Error string/object |
| `makeCall(...)` | `Call` object | Error string/object |
| `answerCall(call)` | Response data | Error string/object |
| `hangupCall(call)` | Response data | Error string/object |
| `holdCall(call)` | Response data | Error string/object |
| `muteCall(call)` | Response data | Error string/object |

### Edge Cases

**makeCall Edge Case**: Native module may return `true` instead of call data:
```javascript
makeCall(sim, destination, callSettings, msgData) {
    return new Promise((resolve, reject) => {
        NativeModules.TeleModule.makeCall(sim, destination, callSettings, msgData, (successful, data) => {
            if (successful) {
                if (data === true) {
                    data = { id: 1 };  // Edge case handling
                }
                resolve(new Call(data));
            } else {
                reject(data);
            }
        });
    });
}
```

## Alternatives

### Option 1: Standard Error-First Callbacks

```javascript
answerCall(call, callback) {
    NativeModules.TeleModule.answerCall(call.getId(), (error, data) => {
        callback(error, data);
    });
}
```

**Pros**: Node.js standard pattern  
**Cons**: Not Promise-compatible, requires callback hell for chaining

### Option 2: Separate Success/Error Callbacks

```javascript
answerCall(call, onSuccess, onError) {
    NativeModules.TeleModule.answerCall(call.getId(), (successful, data) => {
        if (successful) onSuccess(data);
        else onError(data);
    });
}
```

**Pros**: Clear separation  
**Cons**: Two callbacks to manage, not Promise-compatible

### Option 3: Direct Promise from Native

If native module supported Promises directly (not available in current React Native):

```javascript
// Ideal but not possible
const result = await NativeModules.TeleModule.answerCall(call.getId());
```

**Pros**: Cleanest API  
**Cons**: Not supported by React Native bridge

## Error Handling Best Practices

### For Library Maintainers

1. **Wrap errors in Error objects**:
   ```javascript
   if (!successful) {
       reject(new Error(typeof data === 'string' ? data : JSON.stringify(data)));
   }
   ```

2. **Include method name in error**:
   ```javascript
   reject(new Error(`answerCall failed: ${data}`));
   ```

3. **Preserve stack traces**: Capture and include in error

4. **Document error formats**: List possible error messages and meanings

### For Application Developers

1. **Always use try/catch** with async/await:
   ```javascript
   try {
       await endpoint.answerCall(call);
   } catch (error) {
       // Handle error
   }
   ```

2. **Check error type**: Error may be string or object

3. **Log full error**: Include data for debugging

4. **Graceful degradation**: Handle failures appropriately

### Unit Tests

```javascript
test('answerCall resolves on success', async () => {
    NativeModules.TeleModule.answerCall.mockImplementation((id, callback) => {
        callback(true, { success: true });
    });
    
    const result = await endpoint.answerCall(mockCall);
    expect(result).toEqual({ success: true });
});

test('answerCall rejects on failure', async () => {
    NativeModules.TeleModule.answerCall.mockImplementation((id, callback) => {
        callback(false, 'Native error');
    });
    
    await expect(endpoint.answerCall(mockCall)).rejects.toThrow('Native error');
});
```

### Integration Tests

- Test actual native module behavior
- Verify error messages are meaningful
- Test edge cases (null data, unexpected formats)
