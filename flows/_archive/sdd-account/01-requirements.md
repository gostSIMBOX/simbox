# Requirements: SIP Account Management

> Internal service logic for SIP account creation, registration, and lifecycle management.

## Overview

This document specifies the requirements for the SIP account management module in flutter_nmsip. Accounts represent SIP identities with credentials and registration state.

## Business Context

**Problem**: Applications need to manage multiple SIP accounts with different providers, handle registration lifecycle, and track registration status.

**Solution**: Account abstraction with configuration DTO, separate registration flow, and status tracking via events.

## Stakeholders

- **Developers**: Need clean API for account operations
- **Application**: Multi-account support (e.g., personal + work)
- **End Users**: Reliable registration, clear status feedback

## Functional Requirements

### FR-1: Account Creation

The system SHALL create SIP accounts with full configuration:
- **Required fields**: name, username, domain, password
- **Optional fields**: proxy, transport, regServer, regTimeout, regHeaders, regContactParams
- Return Account object with unique ID
- Support custom SIP headers via regHeaders map

**Acceptance Criteria**:
- [ ] Account created with valid credentials
- [ ] Account ID assigned by native layer
- [ ] Configuration serialized via AccountConfigurationDTO
- [ ] Custom headers supported (regHeaders)
- [ ] Transport defaults to TCP if not specified
- [ ] regTimeout defaults to 3600 seconds

### FR-2: Account Registration

The system SHALL register accounts with SIP server:
- `registerAccount(account, renew: bool)`: Register or renew registration
- renew=true (default): Register/renew with server
- renew=false: Unregister from server
- Broadcast registration status changes via events

**Acceptance Criteria**:
- [ ] Registration initiated via Intent to service
- [ ] Callback ID tracked for async response
- [ ] EVENT_REGISTRATION_CHANGED broadcast on status change
- [ ] Supports manual unregister (renew=false)

### FR-3: Registration Status Tracking

The system SHALL track registration status:
- status: bool (registered/unregistered)
- code: Int? (SIP status code, e.g., 200, 401, 403)
- reason: String? (error message)
- expiration: Int? (seconds until expiry)
- retryAfter: Int? (seconds before retry)

**Acceptance Criteria**:
- [ ] Status updated via registration_changed events
- [ ] AccountRegistration model embedded in Account
- [ ] Status code preserved for debugging
- [ ] Expiration tracked for proactive renewal

### FR-4: Account Deletion

The system SHALL delete accounts and cleanup resources:
- `deleteAccount(account)`: Remove account by ID
- Release native resources
- Stop receiving events for deleted account

**Acceptance Criteria**:
- [ ] Account ID passed to service
- [ ] Native resources released
- [ ] Account removed from endpoint state
- [ ] No further events for deleted account

### FR-5: Account Serialization

The system SHALL serialize accounts for cross-layer communication:
- fromMap(Map<String, dynamic>): Parse from JSON-like map
- toMap(): Convert to Map for transmission
- Preserve nested AccountRegistration
- Equality by ID only

**Acceptance Criteria**:
- [ ] fromMap parses all fields correctly
- [ ] toMap includes all configuration
- [ ] Nested registration serialized
- [ ] hashCode/== by ID only

## Non-Functional Requirements

### NFR-1: Security

- Passwords never logged or exposed in toString()
- Credentials transmitted securely to native layer
- No credential caching in Dart layer

### NFR-2: Reliability

- Registration retry logic handled by native layer
- Status events broadcast even during network changes
- Account ID uniqueness guaranteed

### NFR-3: Performance

- Account creation < 500ms
- Registration response < 2s (network dependent)
- No blocking operations on main thread

### NFR-4: Multi-Account Support

- Support multiple concurrent accounts
- Each account has independent registration
- Account ID uniquely identifies within endpoint

## Dependencies

- **endpoint-management**: Requires initialized SIP endpoint
- **native-bridge**: AccountConfigurationDTO, PjActions
- **event-streaming**: registration_changed events

## Out of Scope

- Call operations (see sdd-call)
- NAT traversal (handled by native layer)
- Account persistence (app responsibility)
