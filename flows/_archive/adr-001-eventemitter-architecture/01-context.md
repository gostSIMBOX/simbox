# ADR 001: EventEmitter Architecture

> **Status**: DRAFT  
> **Type**: Enabling  
> **Generated by**: /legacy analysis

---

## Context

The react-native-tele module needs to provide an event-driven API to notify applications of telephony events (incoming calls, state changes, call termination, etc.).

React Native provides `DeviceEventEmitter` for native-to-JavaScript event communication. The native Android module emits events via `DeviceEventEmitter`, which the JavaScript layer receives.

However, the Endpoint class extends Node.js `EventEmitter` and re-emits events received from DeviceEventEmitter, creating a two-layer event system:

```
Native Module → DeviceEventEmitter → Endpoint (EventEmitter) → Application
```

## Problem

How should the module expose events to applications?

**Options Considered**:
1. Use only DeviceEventEmitter (direct subscription)
2. Use only EventEmitter (custom event bridge)
3. Use both (current implementation)

## Decision

**Chosen**: Use both DeviceEventEmitter and EventEmitter (Option 3)

Endpoint extends Node.js EventEmitter and automatically subscribes to DeviceEventEmitter events in the constructor:

```javascript
import { EventEmitter } from 'events';

export default class Endpoint extends EventEmitter {
    constructor() {
        super();
        
        DeviceEventEmitter.addListener('TeleCallReceived', this._onCallReceived.bind(this));
        DeviceEventEmitter.addListener('TeleCallChanged', this._onCallChanged.bind(this));
        DeviceEventEmitter.addListener('TeleCallTerminated', this._onCallTerminated.bind(this));
        // ... more listeners
    }
    
    _onCallReceived(data) {
        this.emit('call_received', new Call(data));
    }
}
```

## Consequences

### Positive

1. **Familiar API**: Node.js EventEmitter is well-known and documented
2. **Multiple Listeners**: Applications can subscribe multiple times to same event
3. **Standard Methods**: Supports `on()`, `off()`, `once()`, `removeListener()`, etc.
4. **Event Transformation**: Can transform raw native data into Call objects before emitting
5. **Encapsulation**: Native event names (`TeleCallReceived`) hidden from applications
6. **Type Safety**: Can wrap data in proper classes (Call, Message, Account)

### Negative

1. **Extra Layer**: Additional event forwarding adds complexity
2. **Memory Leak Risk**: Event listeners added in constructor are never removed
3. **Two Event Names**: Confusion between native names (`TeleCallReceived`) and public names (`call_received`)

### Neutral

1. **Constructor Side Effects**: Simply instantiating Endpoint subscribes to native events
2. **No Cleanup Method**: No `destroy()` method to unsubscribe from DeviceEventEmitter

## Implementation Details

### Event Mapping

| Native Event | Public Event | Data Type |
|--------------|--------------|-----------|
| `TeleCallReceived` | `call_received` | Call |
| `TeleCallChanged` | `call_changed` | Call |
| `TeleCallTerminated` | `call_terminated` | Call |
| `TeleCallScreenLocked` | `call_screen_locked` | boolean |
| `TeleMessageReceived` | `message_received` | Message (not imported) |
| `TeleConnectivityChanged` | `connectivity_changed` | boolean |

### Known Issues

1. **Missing Imports**: `_onConnectivityChanged` references `Account` class, `_onMessageReceived` references `Message` class, but neither are imported.

2. **No Cleanup**: If Endpoint is instantiated multiple times, old listeners remain active:
   ```javascript
   // Each call creates new listeners that are never removed
   const endpoint1 = new Endpoint();
   const endpoint2 = new Endpoint();
   // Both endpoints receive all events
   ```

## Recommendations

### For Library Maintainers

1. **Add `destroy()` method** to clean up DeviceEventEmitter listeners:
   ```javascript
   destroy() {
       DeviceEventEmitter.removeAllListeners('TeleCallReceived');
       DeviceEventEmitter.removeAllListeners('TeleCallChanged');
       // ... etc
   }
   ```

2. **Fix missing imports** or remove handlers for unused events

3. **Document singleton pattern** if only one Endpoint should exist

### For Application Developers

1. **Use single Endpoint instance** throughout application lifecycle
2. **Don't instantiate multiple times** to avoid duplicate event handling
3. **Be aware of memory leak** if creating/destroying Endpoint dynamically

## Alternatives

### Option 1: DeviceEventEmitter Only

```javascript
// Application subscribes directly
DeviceEventEmitter.addListener('TeleCallReceived', (data) => {
    const call = new Call(data);
});
```

**Pros**: Simpler, no extra layer  
**Cons**: Native event names exposed, no transformation, less discoverable

### Option 2: EventEmitter Only (Custom Bridge)

```javascript
// Manual event bridge without DeviceEventEmitter auto-subscription
class Endpoint extends EventEmitter {
    subscribeToNativeEvents() {
        // Explicit subscription method
    }
}
```

**Pros**: More control, explicit lifecycle  
**Cons**: More boilerplate, requires manual subscription
