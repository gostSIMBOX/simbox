# ADR 001: EventEmitter Architecture - Consequences

## Technical Consequences

### Architecture Impact

- **Enabling**: Provides clean event API for applications
- **Constraint**: Requires maintaining two event layers
- **Risk**: Memory leak if Endpoint instantiated multiple times

### Code Impact

Files affected:
- `src/Endpoint.js` - Constructor subscribes to 6 DeviceEventEmitter events
- `src/tele_endpoint.js` - Alternative implementation with same pattern

### Testing Impact

- Unit tests must mock both EventEmitter and DeviceEventEmitter
- Event listener cleanup should be tested
- Multiple instantiation behavior should be documented

## Operational Consequences

### Runtime Behavior

- Events flow: Native → DeviceEventEmitter → Endpoint → Application
- All Endpoint instances receive all events (no filtering)
- No way to unsubscribe from native events without destroying Endpoint

### Performance

- Minimal overhead (event forwarding is synchronous)
- Memory usage increases with each Endpoint instantiation

## Security Considerations

- No security implications identified
- Events are internal to application scope

## Documentation Impact

Must document:
1. Event mapping table (native → public names)
2. Singleton recommendation
3. Memory leak warning
4. Available events and their data types

## Future Considerations

### If Changed

If we ever remove EventEmitter layer:
- Breaking change for all applications
- Must update all event subscription code
- Loss of event transformation capability

### Migration Path

To fix memory leak without breaking changes:
1. Add optional `destroy()` method
2. Document singleton pattern
3. Add deprecation warning if multiple instances created
