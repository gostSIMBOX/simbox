# ADR 002: Dual Endpoint Strategy - Consequences

## Technical Consequences

### Architecture Impact

- **Enabling**: Supports both SIP and cellular telephony
- **Constraint**: Must maintain two separate codebases
- **Risk**: Feature divergence and inconsistency

### Code Impact

Files affected:
- `src/Endpoint.js` - Primary PJSIP implementation (400+ lines)
- `src/tele_endpoint.js` - Android Telecom implementation (200+ lines)
- `src/Call.js` - Shared call representation
- `src/index.js` - Export configuration

### Testing Impact

- Must test both implementations separately
- Integration tests need both PJSIP and Android Telecom environments
- Event handling tests must account for naming differences

## Operational Consequences

### Runtime Behavior

- Applications choose one implementation at build time
- Both cannot be used simultaneously (would cause conflicts)
- Event listeners from both may interfere if both instantiated

### Performance

- Endpoint.js: Depends on PJSIP library performance
- tele_endpoint.js: Depends on Android Telecom framework
- No significant overhead from dual implementation (only one used per app)

## Maintenance Consequences

### Development Effort

- Bug fixes may need to be applied to both implementations
- Feature requests must be evaluated for both
- Documentation must cover both use cases

### Version Control

- Both implementations versioned together
- Breaking changes in one may affect the other
- Changelog must distinguish which implementation affected

## Documentation Impact

Must document:
1. **Use case comparison**: When to use which implementation
2. **Feature matrix**: Which features available in each
3. **Event mapping**: Different event names and states
4. **Migration guide**: How to switch between implementations
5. **Import examples**: Correct import paths for each

## Developer Experience

### Confusion Points

1. **Similar names**: Both are "Endpoint" classes
2. **Event differences**: `TeleCallReceived` vs `teleCallReceived`
3. **Import paths**: Unclear which file to import
4. **Feature gaps**: tele_endpoint.js has fewer methods

### Improvements Needed

1. Rename or namespace the classes differently
2. Create comparison table in README
3. Add deprecation warnings if one is preferred
4. Provide migration tools if merging in future

## Security Considerations

- Both implementations require same Android permissions
- No additional security risks from dual implementation
- Native module validation required for both

## Future Considerations

### If Merged

Migration to unified Endpoint would require:
- Major version bump (breaking change)
- Automatic event name translation
- Configuration option for telephony backend
- Extensive testing on both SIP and cellular

### If Deprecated

Deprecating one implementation:
- Announce deprecation timeline (6-12 months)
- Provide migration guide
- Maintain during deprecation period
- Remove in next major version

## Stakeholder Impact

### Application Developers

- Must understand difference to choose correctly
- May need to switch if requirements change
- Benefit from having appropriate tool for use case

### Library Maintainers

- Increased maintenance burden
- Must track feature parity
- More complex release process

### End Users

- No direct impact (implementation is internal)
- Benefit from appropriate telephony support
- May experience inconsistencies if app switches implementations
