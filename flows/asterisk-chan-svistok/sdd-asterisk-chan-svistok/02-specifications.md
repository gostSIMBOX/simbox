## Overview

The migration separates the stable upstream implementation from the Svistok
overlay without writing to either source tree. The supplied
`asterisk-chan-dongle` checkout is the authoritative upstream baseline. Legacy
is the behavioral oracle and the sole source for Svistok-specific code.

The complete file inventory identifies 52 source/header paths in the final
module's transitive source closure. Twelve are new, 28 are modified, and 12 are
byte-identical to upstream. The remaining 109 legacy entries form an explicit
`DO NOT COPY` manifest.

## Affected Systems

## Architecture

### Component Diagram

```text
read-only legacy sources ──> legacy oracle executable(s) ──> golden results
          │                                                    │
          └─> exact copy receipt ─> AST extraction ─> src overlay-only code
                                                              │ compare
                                                              ▼
read-only asterisk-chan-dongle ──> baseline slices ─────> migrated module
                │                              ▲               ▲
                └── unchanged public API ──────┘    generated static bridges
```

### Layers

1. **Upstream layer** — unchanged source bodies are compiled from files under
   `asterisk-chan-dongle`; those files are neither copied nor edited.
2. **Svistok overlay** — only project-new definitions and legacy-changed
   definitions live under `src`. A full legacy copy exists there only at the
   recorded copy-first checkpoint; extraction removes every upstream-equivalent
   source unit before the final overlay is accepted.
3. **Compatibility layer** — modified types, declarations, include guards, and
   static-only bridges allow upstream bodies and overlay bodies to share one
   ABI and one state model.
4. **Verification layer** — inventory checks, exact-copy receipts,
   characterization tests, symbol checks, and optional hardware integration.

## Source-Closure Rules

### Root translation units

The final module starts with these 19 legacy objects/sources:

```text
app.c at_command.c at_parse.c at_queue.c at_read.c at_response.c
chan_dongle.c channel.c char_conv.c cli.c helpers.c manager.c
memmem.c ringbuffer.c cpvt.c dc_config.c pdu.c mixbuffer.c pdiscovery.c
```

`single.c`, test programs, and tools are not linked into `chan_dongle.so` and
are excluded.

### Recursive local includes

Every existing project-local quoted include is traversed recursively. This is
required because legacy directly includes multiple `.c` files. The exact
non-obvious chains are recorded in `02-file-inventory.md`.

### Generated configuration

Legacy `config.h` is a generated compile input, not migration source. It is not
copied. Required macros must be generated by the target build or supplied by a
new target-owned compatibility configuration. Their effective values are
captured in the characterization/build manifest.

## File Migration Semantics

### New files

The 12 `NEW` module files are copied byte-for-byte from legacy into `src`, with
subdirectory identity preserved where it prevents name collisions or records
provenance. Any later include-path adaptation happens in a separate recorded
change.

### Modified files

Each of the 28 `MODIFIED` module files follows this mandatory sequence:

1. Copy the legacy file byte-for-byte into `src`.
2. Record legacy path, baseline path, legacy SHA-256, copied SHA-256, mode, and
   copy timestamp in a provenance manifest.
3. Verify both hashes match before editing the copy.
4. Adapt include names/paths so byte-identical headers and implementations are
   resolved from `asterisk-chan-dongle`.
5. Mechanically extract the overlay according to the syntax-aware ownership
   manifest. Keep complete new/modified atomic units and physically remove all
   upstream-equivalent definitions, declarations, macros, and inline bodies
   from the checked-in `src` copy.
6. Adapt includes and add only the minimum target-owned declarations required
   to make the extracted overlay a valid source file. Unchanged public
   declarations come from baseline headers rather than copied legacy text.
7. Record every retained source range and every target-authored adapter range;
   no "inseparable dependency" exception may retain an equivalent upstream
   implementation in `src`.
8. Run the source-overlay purity check before compilation. A successful
   generated slice is not a substitute for this check.

### Identical files

The 12 byte-identical module files are never copied to `src`. The target build
compiles/includes them directly from `asterisk-chan-dongle`.

### Excluded files

All 109 entries in the `DO NOT COPY` inventory are prohibited as copy sources
for `src`. Tests and build support needed by the new project must be newly
authored in the target tree, not copied from excluded legacy paths.

## Function and Symbol Partitioning

### Manifest model

Before adapting a modified translation unit, create a manifest entry for every
source-level atomic unit: function/data definition, declaration, type,
enumerator group, macro, and inline implementation.

| Field | Meaning |
|---|---|
| `legacy_file` / `baseline_file` | Provenance paths |
| `symbol` / `kind` / `linkage` | Unit identity; linkage where applicable |
| `body_relation` | New, modified, syntax/token equivalent, removed, or target-authored adapter |
| `dependency_relation` | Calls/reads changed state, or independent |
| `owner` | Baseline slice or checked-in Svistok overlay |
| `public_symbol` | Final exported/link-visible name |
| `verification` | Golden scenario, unit test, ABI check, or manual rationale |

### Ownership rules

- A new or body-modified definition is owned by the Svistok overlay and retains
  the legacy implementation text.
- Every body-equivalent function is owned by the upstream slice, including a
  function whose dependency closure reaches changed static code or state. Such
  dependencies are redirected through generated bridges; the unchanged
  function body itself is absent from the checked-in Svistok overlay.
- An upstream-equivalent unit must also be absent from the physical files under
  `src`; ownership is enforced at source-tree level before build composition.
- Each final externally visible symbol has exactly one strong owner.
- Mutable file/global state has exactly one canonical storage owner; upstream
  and overlay code must not receive independent copies of the same state.
- Runtime dispatch (`dlsym`, weak-symbol selection, link-order selection, or
  per-call conditionals) is prohibited. Routing is fixed at build/link time.

### Baseline slicing and physical overlay extraction

For each modified translation unit, final build inputs are composed as follows:

1. A **baseline slice** is generated from the corresponding
   `asterisk-chan-dongle` file. It retains upstream-owned definitions and
   removes definitions replaced or removed by Svistok.
2. The checked-in **Svistok overlay source** under `src` is produced from the
   receipt-verified legacy copy by syntax-aware extraction. It contains only
   new/modified legacy-owned atomic units plus explicitly manifest-listed new
   adapter text.
3. The overlay source is compiled without source filtering, either directly or
   through a generated non-filtering composition unit that includes the whole
   overlay and appends only manifest-listed bridges/accessors. The build must
   not regenerate a second Svistok slice from a full mixed legacy copy.

Baseline slicing and overlay extraction must be syntax-aware (C parser/AST or
an equivalently verified definition-range manifest), not regex-based. Generated
baseline slices and bridges live in the build directory, never in `src`, and
preserve source-line mapping for diagnostics. The extraction manifest maps each
retained legacy source range to its final `src` range and separately identifies
new adapter ranges. Thus unchanged bodies exist only in
`asterisk-chan-dongle`-derived inputs, while changed bodies remain traceable to
legacy.

No forwarder is permitted for ordinary unchanged external functions. The
baseline slice exports the original name and calls from the overlay resolve to
that symbol normally. For example, the definition of equivalent
`app_register()` is removed from `src/app.c`; any overlay call to
`app_register()` links directly to the baseline-slice definition. A generated
bridge is introduced only where C linkage prevents a direct cross-layer call:

- an unchanged `static` function needed by changed code receives an external
  wrapper in the upstream slice;
- a changed `static` function needed by unchanged code receives an external
  wrapper appended after the overlay inside its generated composition unit,
  and the generated upstream slice redirects only the call site/declaration to
  that wrapper without replacing the unchanged caller body;
- shared `static` or file-scope mutable data has one canonical owner and is
  reached from the other slice through generated accessors;
- a `static inline` or macro-defined implementation in a modified header is
  partitioned by the same ownership rule and verified after preprocessing.

Bridge names use a reserved target-owned prefix and are absent from the public
Asterisk module API. Bridge generation and call redirection must be represented
explicitly in the symbol manifest.

## Function/File Separation Added by Requirements 1.4

### Physical layout

The final target-owned layout separates three kinds of implementation:

```text
src/
├── svistok/                 # functions absent from dongle and Svistok hooks
│   ├── <module>.c
│   ├── <module>.h
│   └── hooks/<module>.c
├── dongle/                  # proxy-only composition fragments
│   └── <module>.c
└── <module>.c               # only inseparable modified legacy functions
```

- `src/svistok/<module>.c` groups complete legacy definitions that do not exist
  as functions in baseline. Grouping is by the original translation unit; it
  does not put every function in a separate one-function file.
- `src/svistok/hooks/<module>.c` contains only the Svistok additions extracted
  from safely decomposed modified functions.
- `src/dongle/<module>.c` contains only mechanical wrappers: argument/result
  adaptation, hook calls, and exactly one call to a generated baseline entry.
  It contains no persistence, state-machine, parsing, logging, or other
  Svistok business logic itself.
- Remaining root `src/<module>.c` files contain only modified functions whose
  changes cannot be represented by the wrapper contract without changing
  legacy behavior.
- Existing compatibility headers are not automatically proxy files. New-only
  declarations move to `src/svistok/<module>.h`; ABI-modified types remain in
  compatibility headers. A header moves to `src/dongle` only if all its
  declarations are private to a proxy fragment.

Static new functions and static proxy functions remain in the original logical
translation unit through non-filtering `#include` composition. Physical file
separation must not turn a legacy `static` symbol into public module API.

### Composition and symbol rules

1. A renamed baseline entry is generated only for the 14 approved decomposed
   functions. It has hidden visibility and must not appear in the public module
   symbol set.
2. Each proxy owns the original symbol name and contains one syntactic call to
   its matching baseline entry. For a `static` original, both files are included
   into the same logical composition and the original remains non-public.
3. Hook files may call Svistok services but never call the baseline entry; this
   prevents accidental double invocation or recursion.
4. Tests instrument the generated baseline entry and assert exactly one runtime
   invocation on success and every covered failure path.
5. Source ownership scans follow included fragments and verify their physical
   paths: `new` under `src/svistok`, `proxy` under `src/dongle`, and inseparable
   `modified` under the root overlay.

### Source-overlay purity verification

The purity verifier operates on the final checked-in `src`, before build
composition:

1. Parse each final overlay file in its target preprocessing context.
2. Consider only units whose spelling/source range is physically located under
   `src`; units imported through baseline headers do not become overlay-owned.
3. Match every local unit against the ownership/extraction manifest.
4. Require every legacy-owned local unit to be `new` or `modified` and verify
   its normalized legacy provenance hash.
5. Permit target-authored includes, guards, declarations, and adapters only
   when separately classified as `target-authored adapter` with a stated need.
6. Fail on any equivalent, unclassified, duplicated, or owner-mismatched local
   unit and report its path, range, kind, identity, and baseline match.

Comments and licence notices are not executable/declarative ownership units;
they may remain only where they apply to retained code or record provenance.
They cannot contain disabled duplicate implementations used to bypass the
purity check.

### Header and ABI compatibility

`chan_dongle.h`, `cpvt.h`, `dc_config.h`, and other modified headers change
structure layouts and declarations. Header extraction uses the same atomic-unit
ownership rules as `.c` extraction: a complete modified type/macro/declaration
is retained because it is one changed syntactic unit, while equivalent
declarations, macros, and inline bodies are removed and obtained from baseline
headers. Target-authored overlay headers use distinct guards and explicitly
include compatible baseline headers where possible.

An upstream body may only be reused after it is compiled against the canonical
Svistok-compatible type definitions. Baseline-slice include directives are
syntax-aware rewritten or pre-included so the selected canonical overlay ABI is
used instead of an incompatible baseline-local definition. ABI assertions
prove that both baseline-owned and overlay-owned objects share one layout.

The build must fail on:

- conflicting type definitions;
- duplicate strong symbols;
- missing overlay/upstream ownership;
- mismatched structure size/offset assertions for shared types;
- unresolved references caused by a sliced static dependency.
- any upstream-equivalent source-level unit physically present under `src`;
- a changed/new function body in the upstream slice;
- unmanifested bridge or mutable-state duplication.

## Characterization Before Migration

### Oracle protocol

1. Build/run harnesses outside the legacy directory; all outputs go to a target
   build directory or temporary directory.
2. Execute the harness against legacy sources first.
3. Store normalized inputs, outputs, return values, state transitions, and
   relevant emitted events as golden fixtures.
4. Run the identical harness against the migrated composition.
5. Compare deterministic fields exactly; normalize timestamps, pointers,
   device paths, and other environment-dependent values explicitly.

### Test tiers

| Tier | Scope | Before-transfer expectation |
|---|---|---|
| T0 Inventory | paths, hashes, include closure, Git cleanliness | Mandatory |
| T1 Pure components | PDU, AT parsing, character conversion, ring/mix buffers | Mandatory where host-compilable |
| T2 Stateful components | limits, selection, statistics, queue transitions | Mandatory with filesystem/time/Asterisk stubs |
| T3 Module contract | exported symbols, ABI sizes/offsets, load/unload boundary | Mandatory in compatible Linux/Asterisk environment |
| T4 Hardware | modem discovery, calls, SMS/USSD, firmware operations | Run when equipment/environment is available; otherwise preserve fixtures and document gap |

Legacy stability makes it the behavioral oracle, but it does not make host- or
hardware-dependent observations deterministic. Fixture normalization must be
explicit and minimal.

## Data Flow

```text
legacy input vector
  -> legacy harness
  -> normalized golden result
  -> migrated harness
  -> normalized actual result
  -> exact/semantic comparator
  -> pass or documented environment gap
```

## Behavior Specifications

### Happy Path

1. Inventory script reproduces the 52/109 partition.
2. Characterization harness records legacy behavior without dirtying legacy.
3. New and modified files are copied according to the inventory and exact-copy
   receipts pass at the intermediate copy-first checkpoint.
4. Modified copies are physically reduced to new/changed atomic units; the
   source-overlay purity audit proves zero equivalent units remain in `src`.
5. Unchanged files and external symbols resolve directly from baseline.
6. Baseline translation units are sliced only where Svistok replaces/removes
   definitions; static cross-layer dependencies receive generated bridges.
7. Target compiles with one owner per symbol and compatible shared types.
8. Golden comparisons pass for all available tiers.

### Edge Cases

| Case | Trigger | Expected behavior |
|---|---|---|
| Direct `.c` include | Legacy includes implementation text | Included file remains in module closure and is migrated/reused by its own classification |
| Same basename in several directories | Root, `old/`, and `programmator/` contain similar files | Resolve by actual include path; only reachable path enters closure |
| Generated `config.h` | Present only in legacy | Do not copy; reproduce effective configuration in target build |
| Unchanged function calls changed static code/state | Cross-slice dependency cannot link directly | Keep the unchanged body upstream and redirect the dependency through a generated Svistok bridge/accessor |
| Changed function calls unchanged static code/state | Cross-slice dependency cannot link directly | Keep the unchanged implementation/state upstream and expose a generated upstream bridge/accessor |
| Equivalent external function appears in a modified file | Example: `app_register()` in `app.c` | Remove its definition physically from `src`; resolve the original name from the baseline slice with no forwarding wrapper |
| Equivalent declaration/macro/inline remains in overlay header | File-level copy passed but header is still mixed | Fail source-overlay purity; extract at the complete syntactic-unit level and use the compatible baseline header/API |
| Modified shared struct | Baseline function consumes `pvt`/`cpvt` | Compile against canonical compatibility ABI and assert layout |
| Duplicate symbol | Both slices define same public name | Fail build; fix ownership manifest, never rely on link order |
| Proxy recursively calls its original public name | Rename/routing error | Fail wrapper instrumentation/link audit; proxy may call only its hidden matching baseline entry |
| Baseline call fails | Decomposed function returns an error | Run only hooks whose documented legacy position occurs on that path; preserve the exact legacy return/result and call count |
| Static new/proxy function moved physically | Separate file would normally change linkage | Include the fragment non-filteringly in its original logical translation unit and keep it `static` |
| Root overlay becomes empty after split | All definitions moved to baseline, `svistok`, or `dongle` | Remove the empty root source from checked-in/build inputs rather than retain a forwarding shell |
| Artifact resembles source | `.o`, `.gch`, ELF, Autotools/SVN output | Keep in inventory, never copy |
| Missing Asterisk/hardware environment | Higher-tier test cannot run | Complete lower tiers and record exact blocked tier; do not claim full parity |

## Error Handling

| Error | Response |
|---|---|
| Legacy or baseline becomes dirty | Stop immediately and report changed paths |
| Copy hash mismatch | Delete/recreate only the target copy, then reverify; never edit legacy |
| Inventory count/path drift | Stop and regenerate/review specification before copying |
| Unparseable C definition during slicing | Mark translation unit blocked for manual manifest review; do not regex-slice |
| Overlay extraction cannot produce valid standalone source | Stop and revise ownership/adapter design; do not retain equivalent legacy code as a workaround |
| Equivalent source unit found under `src` | Fail before compilation and report path, range, kind, symbol/macro, and matching baseline provenance |
| Proxy contains non-routing business logic | Fail proxy-purity verification and move the logic to its Svistok hook or retain the whole modified body |
| Proxy calls baseline zero or multiple times | Fail static call-count verification and instrumented characterization |
| Function marked decomposable changes golden trace | Reclassify it as inseparable; do not weaken the golden comparison |
| Golden mismatch | Keep legacy as authority; diagnose migration divergence before proceeding |
| ABI assertion failure | Stop linking and revise compatibility ownership |

## Migration and Rollback

- No migration operation changes legacy or baseline.
- All target changes remain reviewable in the nested
  `libsCpp/asterisk-chan-svistok` Git worktree.
- Exact-copy receipts make it possible to distinguish copied legacy state from
  later extraction/adaptation; the receipt does not require the final overlay
  to remain a full-file copy.
- Rollback removes/reverts only target-owned generated baseline slices, overlay
  files, tests, manifests, and build changes; source trees remain intact.

## Confirmed Design Decisions

- On 2026-08-25 the user confirmed strict function ownership: all unchanged
  function bodies originate from upstream, while changed/new bodies originate
  from legacy.
- Cross-slice `static` functions and state are connected with generated
  build-time bridges/accessors rather than copying unchanged bodies.
- On 2026-08-25 the user clarified and approved requirements 1.3: final `src`
  itself is an overlay-only source tree. Build-time removal of an equivalent
  body from a generated Svistok slice does not satisfy this constraint.
- Equivalent external functions are absent from `src` and retain their original
  symbol names in baseline-derived objects; `app_register()` is the explicit
  acceptance example.
- The existing Clang JSON-AST ownership/slicing toolchain is extended for
  physical overlay extraction and purity verification; it must satisfy the
  ownership, provenance, and verification rules above.
- On 2026-08-26 the user approved requirements 1.4: new functions are
  physically separated, safely composable modified functions call baseline
  once through proxy-only files under `src/dongle`, and inseparable functions
  retain their complete legacy bodies.
- The 6/14/87 partition in this specification is closed for implementation:
  six false-modified definitions return to direct baseline ownership, fourteen
  functions use hook/proxy composition, and 87 remain inseparable.
