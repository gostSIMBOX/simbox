## Business Requirements

### BR-1: Multi-Device Management

The system SHALL manage multiple SIM-bank devices simultaneously.

**Rationale**: Production environments deploy multiple SIM-banks (SMB128, SMB32 models) that need centralized management.

**Source**: `simbank.Manager` maintains `map[uint]*Client` for device instances.

### BR-2: Periodic Status Monitoring

The system SHALL monitor SIM-bank status at regular intervals.

**Rationale**: Operators need up-to-date information about SIM card status, signal strength, and device availability.

**Source**: `monitorLoop()` with configurable `PollingInterval` (default: 30s).

### BR-3: Remote Slot Control

The system SHALL allow remote control of individual SIM slot power.

**Rationale**: Operators need to reset SIM cards remotely without physical access.

**Source**: `SetPower(simBankID, slotID, power)` method.

### BR-4: USSD Command Execution

The system SHALL support sending USSD commands to SIM cards.

**Rationale**: USSD commands are required for balance checks, tariff changes, and network operations.

**Source**: `SendUSSD(simBankID, slotID, command)` method.

### BR-5: State Persistence

The system SHALL persist SIM-bank and slot state to database.

**Rationale**: State must survive restarts and provide audit trail.

**Source**: `updateSlots()` upserts to `sim_slots` table.

### BR-6: Event Logging

The system SHALL log all errors and significant events.

**Rationale**: Operations team needs visibility into system behavior for troubleshooting.

**Source**: `recordSystemEvent()` writes to `system_events` table.

## Technical Requirements

### TR-1: Concurrent Device Updates

The system SHALL update multiple SIM-banks in parallel.

**Rationale**: Sequential polling would be too slow for large deployments.

**Source**: `updateAllSimBanks()` uses goroutine-per-device with `WaitGroup`.

### TR-2: Graceful Shutdown

The system SHALL support graceful shutdown with context cancellation.

**Rationale**: Clean shutdown prevents data corruption and in-flight operation loss.

**Source**: `context.Context` with `cancel()` in `Stop()`.

### TR-3: Thread-Safe Access

The system SHALL provide thread-safe access to shared device registry.

**Rationale**: Concurrent reads (polling) and writes (device registration) require synchronization.

**Source**: `sync.RWMutex` protecting `clients map`.

### TR-4: HTTP Client Configuration

The system SHALL configure HTTP client with timeout per device.

**Rationale**: Prevent hanging on unresponsive devices.

**Source**: `http.Client` with configurable `Timeout` (default: 10s).

### TR-5: Database Connection Pool

The system SHALL use connection pooling for database access.

**Rationale**: Efficient resource utilization under concurrent load.

**Source**: GORM with `MaxIdleConns=5`, `MaxConns=configurable`.

## Non-Functional Requirements

### NFR-1: Polling Interval

Default polling interval SHALL be 30 seconds.

**Rationale**: Balance between data freshness and system load.

### NFR-2: Retry Logic

The system SHALL retry failed operations with configurable attempts.

**Default**: 3 retry attempts with 5s delay.

### NFR-3: Scalability

The system SHALL support at least 10 concurrent SIM-bank devices.

**Rationale**: Typical deployment size.

### NFR-4: Error Recovery

The system SHALL continue operation despite individual device failures.

**Rationale**: One failing device should not affect others.
