# ADR-001: Platform Interface Pattern

> Architectural Decision Record for using Flutter's platform interface pattern.

## Status

DRAFT

## Type

Enabling

## Context

The flutter_smsussd plugin needs to support multiple platforms (Android, iOS, Web, Linux, macOS, Windows) with varying levels of SMS functionality. Android has full SMS support, iOS has limited support (composer only), and other platforms have no SMS capabilities.

We need an architecture that:
- Provides a single API across all platforms
- Allows platform-specific implementations
- Enables testing without native dependencies
- Follows Flutter plugin best practices

## Decision

Use Flutter's **Platform Interface Pattern** with the `plugin_platform_interface` package.

### Architecture

### Key Components

1. **Abstract Platform Class**: `FlutterSmsussdPlatform`
   - Extends `PlatformInterface` from `plugin_platform_interface` package
   - Uses token-based verification for instance assignment
   - Defines abstract methods for all platform operations
   - Defaults to method channel implementation

2. **Token Verification**:
   ```dart
   static final Object _token = Object();
   
   static set instance(FlutterSmsussdPlatform instance) {
     PlatformInterface.verifyToken(instance, _token);
     _instance = instance;
   }
   ```

3. **Platform Methods**:
   - `getPlatformVersion() -> Future<String?>`
   - `sendSms({phoneNumber, message}) -> Future<bool>`
   - `getSmsMessages() -> Future<List<SmsMessage>>`
   - `getSmsMessagesByPhoneNumber(phoneNumber) -> Future<List<SmsMessage>>`
   - `requestSmsPermissions() -> Future<bool>`
   - `hasSmsPermissions() -> Future<bool>`

4. **Data Models**: `SmsMessage` and `SmsType` defined in platform interface

## Consequences

### Benefits

✅ **Platform Abstraction**: Single API across all platforms
✅ **Testability**: Platform instance can be mocked for unit tests
✅ **Extensibility**: New platforms can be added without modifying core API
✅ **Type Safety**: Token verification prevents unauthorized implementations
✅ **Standard Pattern**: Follows Flutter plugin best practices
✅ **Clear Separation**: Platform-specific code isolated in implementations

### Trade-offs

⚠️ **Complexity**: More files and abstractions than simple implementation
⚠️ **Boilerplate**: Requires token setup and verification code
⚠️ **Indirection**: One extra level of indirection in method calls

### Limitations

⚠️ **Platform Disparities**: Different platforms have different capabilities (Android full, iOS limited, others none)
⚠️ **Runtime Errors**: Some methods throw `UnsupportedError` on platforms without SMS support

## Compliance

- All platform implementations MUST extend `FlutterSmsussdPlatform`
- All implementations MUST be registered via `FlutterSmsussdPlatform.instance = ...`
- All methods MUST maintain the signatures defined in the abstract class
- Data models (`SmsMessage`, `SmsType`) MUST be used consistently across platforms
